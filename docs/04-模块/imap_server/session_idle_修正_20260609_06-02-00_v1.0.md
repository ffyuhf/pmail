## 二、修改前后对比

### 2.1 BUG-2a：错误键删除（内存泄漏）

**修改前（第 40-45 行）**：使用 `logId` 作为键删除 `sync.Map` 条目，但存储键是 `userId`

```go
go func() {
    <-stop
    userConnects.Delete(logId)  // BUG: logId 不是存储键
}()
```

**修改后**：从内层 map 正确删除 `logId`，map 为空时清理外层条目

```go
go func() {
    <-stop
    userConnectsMu.Lock()
    connects.mu.Lock()
    delete(connects.writers, logId)
    if len(connects.writers) == 0 {
        userConnects.Delete(userId)
    }
    connects.mu.Unlock()
    userConnectsMu.Unlock()
}()
```

### 2.2 BUG-2b：硬编码消息数

**修改前（第 60 行）**：始终推送 1

```go
connect.WriteNumMessages(1)
```

**修改后**：通过 `idleNumMessages` 查询实际消息数

```go
connect.writer.WriteNumMessages(idleNumMessages(ctx, userId, connect.mailbox))
```

新增 `idleNumMessages` 函数，复用已有的 `group.GetGroupStatus`。

### 2.3 BUG-2c：缺少 mutex 保护

**修改前**：裸 `map[string]*imapserver.UpdateWriter` 无互斥保护

**修改后**：引入 `idleConnection` 和 `idleConnections` 结构体，使用 `sync.Mutex` 保护

```go
type idleConnection struct {
    writer  *imapserver.UpdateWriter
    mailbox string
}
type idleConnections struct {
    mu      sync.Mutex
    writers map[string]idleConnection
}
```

### 2.4 BUG-2d：缺少 mailbox 跟踪

**修改前**：`IdleNotice` 无法按邮箱精确推送

**修改后**：`idleConnection` 包含 `mailbox` 字段，`idleNumMessages` 按邮箱查询

## 三、变更原因

| BUG 编号 | 问题 | 严重程度 |
|----------|------|----------|
| BUG-2a | 错误键删除导致内存泄漏 | 高 |
| BUG-2b | 硬编码消息数导致客户端显示错误 | 高 |
| BUG-2c | 无 mutex 保护可能导致 panic | 高 |
| BUG-2d | 无法按邮箱精确推送通知 | 中 |

## 四、影响评估

- 内存：修复泄漏，长时间运行后内存不再持续增长
- 功能：IDLE 推送正确的 EXISTS 更新
- 并发安全：mutex 保护避免 panic
- 依赖：新增对 `group.GetGroupStatus` 的调用
