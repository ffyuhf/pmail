## 5.1 文档命名规则

### 5.1.1 命名结构

```
[实体名称]_[文档类型]_[日期]_[时间]_[版本号].md
```

### 5.1.2 各字段说明

| 字段 | 格式 | 说明 | 示例 |
|------|------|------|------|
| 实体名称 | 小写英文+连字符 | 可溯源的代码实体名称（模块/组件/类/函数/文件/目录名） | `imap_server`、`parsemail` |
| 文档类型 | 中文或英文 | 文档用途或修改动作类型 | `计划`、`修改`、`新增`、`重构`、`修正` |
| 日期 | YYYYMMDD | 文档创建或最后修改日期 | `20260609` |
| 时间 | HH-MM-SS | 24小时制，紧接日期之后，用下划线分隔 | `06-00-00` |
| 版本号 | vX.Y | X为主版本号，Y为次版本号 | `v1.0` |

### 5.1.3 完整示例

```
imap_server_Caps_修正_20260609_06-02-00_v1.0.md
parsemail_formatContent_修正_20260609_06-03-00_v1.0.md
```

### 5.1.4 强制规则

- **禁止**使用空格、特殊字符、中文标点
- **禁止**使用模糊、不可读、不可溯源的名称
- **必须**包含可溯源的代码实体名称
- **必须**包含文档类型或修改动作类型
- **必须**包含日期和时间
- **必须**包含版本号

## 5.3 必填元数据字段清单与格式

### 5.3.1 元数据模板

每份文档**必须**在文件开头包含以下元数据：

```markdown
> **版本**: vX.Y  
> **日期**: YYYY-MM-DD  
> **时间**: HH:MM:SS  
> **作者**: [作者名称]  
> **模块**: [所属模块名称]  
> **状态**: 草稿/评审中/已批准/已归档  
> **生效范围**: [适用范围描述]
```

### 5.3.2 字段说明

| 字段 | 是否必填 | 格式要求 | 说明 |
|------|----------|----------|------|
| 版本 | **必填** | vX.Y | 文档当前版本号 |
| 日期 | **必填** | YYYY-MM-DD | 文档创建或最后修改日期 |
| 时间 | **必填** | HH:MM:SS | 24小时制 |
| 作者 | **必填** | 文本 | 文档创建者或最后修改者 |
| 模块 | **必填** | 小写英文+连字符 | 文档所属的代码模块 |
| 状态 | **必填** | 枚举值 | 草稿/评审中/已批准/已归档 |
| 生效范围 | 可选 | 文本 | 文档适用范围描述 |

## 5.4 版本号规则与变更日志模板

### 5.4.1 版本号规则

| 版本号 | 含义 | 示例 |
|--------|------|------|
| 主版本号 (X) | 重大变更、不兼容修改 | v1.0 → v2.0 |
| 次版本号 (Y) | 功能新增、兼容性修改 | v1.0 → v1.1 |
| 修订号 (Z)（可选） | Bug修复、文档修正 | v1.0.1 |

**强制规则**：版本号**必须**连续，**不得**跳跃。

### 5.4.2 变更日志模板

每份文档**必须**包含变更日志章节，格式如下：

```markdown
## 变更日志

| 版本 | 日期 | 时间 | 作者 | 变更内容 | 变更原因 |
|------|------|------|------|----------|----------|
| v1.0 | 2026-06-09 | 06:00:00 | PMail Team | 初始创建 | 新文档建立 |
| v1.1 | 2026-06-09 | 12:00:00 | PMail Team | 补充章节 | 完善规范 |
```

## 5.6 文档读写流程与检查清单

### 5.6.1 文档读取流程

1. **识别文档类型** — 确定文档属于规范/计划/设计/模块中的哪一类
2. **按优先级阅读** — 规范 → 设计 → 实现 → 测试
3. **深度分析** — 理解功能目的、识别关键定义、记录依赖关系
4. **跨文件关联** — 构建依赖图谱、识别数据流向

### 5.6.2 文档写入流程

```
创建/更新计划书 → 审批 → 执行代码修改 → 创建代码修改文档 → 归档
```

### 5.6.3 强制检查清单

**修改前检查**：

- [ ] 已阅读并理解【规范.md】全部内容
- [ ] 已创建或更新【计划书.md】并完成审批
- [ ] 已完成影响范围评估

**修改后检查**：

- [ ] 已创建或更新【代码修改文档】并包含必要章节
- [ ] 已归档至 `docs/` 目录指定子目录
- [ ] 已完成版本标记
- [ ] 代码与文档一致性校验通过（无过时、无矛盾、无遗漏）

### 5.6.4 审核点

| 审核点 | 时机 | 要求 |
|--------|------|------|
| 计划书审批 | 代码修改前 | 必须通过后方可执行 |
| 文档完整性检查 | 每次文档创建/更新后 | 必须包含所有必填章节 |
| 代码文档一致性 | 代码修改完成后 | 必须同步更新关联文档 |
| 归档检查 | 文档完成后 | 必须归档至正确目录 |

## 5.7 质量标准与失效条件

### 5.7.1 质量标准

| 标准 | 说明 | 验证方式 |
|------|------|----------|
| 清晰 | 文档目的明确，一看即懂 | 同行评审 |
| 完整 | 包含所有必要章节和必填字段 | 检查清单校验 |
| 可追溯 | 关联代码文件、行号、函数签名 | 路径引用验证 |
| 一致 | 与代码保持同步，无矛盾 | 代码文档一致性校验 |
| 可审计 | 变更历史完整，版本号连续 | 变更日志审查 |

### 5.7.2 失效条件

以下情况文档视为**无效**，必须立即整改：

1. **命名不符合规范** — 缺少必要字段（实体名称/日期/时间/版本号）
2. **目录位置错误** — 未归档至正确的子目录
3. **缺少必填元数据** — 版本/日期/作者/状态任一字段缺失
4. **版本号跳跃** — 版本号不连续
5. **变更日志缺失** — 无变更记录或记录不完整
6. **代码文档不一致** — 文档描述与实际代码不匹配
7. **计划书缺失** — 代码修改前未创建计划书
8. **审批未通过** — 未经审批即执行的变更

### 5.7.3 整改流程

```
发现失效文档 → 停止相关操作 → 整改文档 → 重新审计 → 通过后继续
```
