### 🔴 #1 [严重] SMTP From 地址伪装检查空实现（发送端）

**文件位置**：
```
server/
└── listen/
    └── smtp_server/
        └── read_content.go  第 67-75 行
```

**问题代码**：
```go
if s.From != "" {
    from := parsemail.BuilderUser(s.From)
    if email.From == nil {
        email.From = from
    }
    if email.From.EmailAddress != from.EmailAddress {
        // 协议中的from和邮件内容中的from不匹配，当成垃圾邮件处理
    }
}
```

**源码验证**：
✅ **确认真实**。此代码位于 `Data()` 函数中，在 `if s.Ctx.UserID > 0`（line 78）之前执行，对发送和接收路径均有效。但实际影响主要在**发送端**：
- 已认证用户可通过 SMTP 发送 envelope From 为 `alice@domain.com` 但 header From 为 `bob@domain.com` 的邮件
- if 块为空，注释声称"当成垃圾邮件处理"但无任何实际处理
- 注释风格偏接收端视角，但代码逻辑对发送端有实际影响

**影响范围**：
已认证用户可伪造 From 头实现邮件身份伪装，可用于钓鱼邮件发送。

**修复建议**：
1. 不匹配时拒绝发送：`return errors.New("from mismatch")`
2. 或至少记录安全告警日志

### 🔴 #2 [严重] Rule UPDATE 缺少 user_id 权限校验

**文件位置**：
```
server/
└── controllers/
    └── rule.go  第 64 行（UPDATE 语句）
```

**问题代码**：
```go
// INSERT 时正确添加了 user_id（第 70 行）
_, err := db.Instance.Exec(db.WithContext(ctx, "insert into rule (name,value,user_id,action,params,sort) values (?,?,?,?,?,?)"),
    p.Name, p.Value, ctx.UserID, p.Action, p.Params, p.Sort)

// UPDATE 时缺少 user_id 条件（第 64 行）
_, err := db.Instance.Exec(db.WithContext(ctx, "update rule set name=? ,value = ? ,action = ?,params = ?,sort = ? where id = ?"),
    p.Name, p.Value, p.Action, p.Params, p.Sort, p.Id)

// DELETE 时正确包含 user_id（第 102 行）
_, err = db.Instance.Exec(db.WithContext(ctx, "delete from rule where id =? and user_id =?"), data.Id, ctx.UserID)
```

**源码验证**：
✅ **确认真实**。UPDATE 的 WHERE 子句仅有 `id = ?`，缺少 `AND user_id = ?`。对比 INSERT 和 DELETE 均正确包含 user_id。

**影响范围**：
IDOR 漏洞。攻击者可修改其他用户的邮件规则。

**修复建议**：
在 UPDATE 的 WHERE 子句中添加 `AND user_id = ?`，使用 `ctx.UserID` 参数。

### 🔴 #3 [严重] IMAP FindUE uid=true 路径缺少 user_id 过滤

**文件位置**：
```
server/
└── services/
    └── detail/
        └── detail.go  第 89-94 行
```

**问题代码**：
```go
func FindUE(ctx *context.Context, groupName string, req list.ImapListReq, uid bool) []models.UserEmail {
    var ue []models.UserEmail
    if uid {
        // uid=true 路径：仅按 id 过滤，无 user_id
        err := db.Instance.Where(Eq{"id": req.UidList}).Find(&ue)
        // ...
    } else {
        // uid=false 路径：包含 user_id 过滤（正确）
```

**源码验证**：

**修复建议**：

### 🟠 #4 [高危] POP3 APOP 认证与 bcrypt 密码不兼容

**文件位置**：
```
server/
└── listen/
    └── pop3_server/
        └── action.go  第 195 行
```

**问题代码**：
```go
// APOP 认证（action.go:195）— 仅用 MD5 比较，不兼容 bcrypt
if user.ID > 0 && digest == password.Md5Encode(user.Password) {

// 对比：PASS 命令（action.go:133）— 使用双算法验证，兼容 bcrypt
ok, needsUpgrade := password.Verify(pwd, user.Password)
```

**源码验证**：
✅ **确认真实**。密码升级为 bcrypt 后，`Md5Encode(bcrypt哈希)` 计算的摘要与客户端计算的 `MD5(时间戳+明文密码)` 永远不匹配。APOP 无类似 PASS 命令的双算法验证和自动升级逻辑。

**影响范围**：
- APOP 用户在密码自动升级后无法通过 POP3 收取邮件
- 没有任何错误提示或回退机制

**修复建议**：
考虑弃用 APOP（POP3 CAPA 中移除），或增加类似 PASS 命令的回退验证逻辑。

### 🟠 #5 [高危] DelByUID 缺少事务 Begin

**文件位置**：
```
server/
└── services/
    └── del_email/
        └── del_email.go  第 117-154 行
```

**问题代码**：
```go
func DelByUID(ctx *context.Context, ids []int) error {
    session := db.Instance.NewSession()
    defer session.Close()
    // 注意：此处缺少 session.Begin()
    for _, id := range ids {
        // ... 删除操作，中途错误调用 session.Rollback()
    }
    session.Commit()
    return nil
}
```

**源码验证**：

### 🟠 #7 [高危] API Token IP 校验生成/验证端格式不一致

**文件位置**：
```
server/
├── controllers/
│   └── login.go  第 147 行（生成时）
└── listen/
    └── http_server/
        └── https_server.go  第 143 行（验证时）
```

**生成时代码**（login.go:147）：
```go
ClientIP: ratelimit.ExtractIP(req.RemoteAddr),  // 输出 "1.2.3.4"（纯 IP）
```

**验证时代码**（https_server.go:143）：
```go
user, err := getLoginInfoByToken(token, r.RemoteAddr)  // 传入 "1.2.3.4:12345"（含端口）
```

**验证时比较**（https_server.go:196）：
```go
if apiToken.ClientIP != "" && apiToken.ClientIP != clientIP {
    return ret, errors.New("token ip mismatch")
}
```

**源码验证**：
✅ **确认真实**。生成端使用 `ratelimit.ExtractIP()` 处理后存入数据库（纯 IP），验证端直接传入 `r.RemoteAddr`（含端口号），格式不一致导致比较永远失败。

**影响范围**：
所有使用 IP 绑定的 API Token 将永远无法通过验证。

**修复建议**：
在 `getLoginInfoByToken` 调用前使用 `ratelimit.ExtractIP(r.RemoteAddr)` 处理 IP 地址。

### 🟠 #8 [高危] Content-Disposition 文件名注入

**文件位置**：
```
server/
└── controllers/
    └── attachments.go  第 48 行
```

**问题代码**：
```go
w.Header().Set("Content-Disposition", fmt.Sprintf("attachment;filename=%s", fileName))
```

**源码验证**：
✅ **确认真实**。`fileName` 直接来自邮件附件元数据，无编码、无转义、无引号包裹。若文件名含 CRLF 可实现 HTTP Header 注入。

**影响范围**：
HTTP Header 注入（CRLF Injection），可能影响浏览器下载行为。

**修复建议**：
1. 使用 RFC 5987 编码：`filename*=UTF-8''urlencoded_name`
2. 至少过滤 `\r` 和 `\n` 字符
3. 用双引号包裹文件名

### 🟡 #10 [中危] CSRF 防护 Origin/Referer 为空时绕过
