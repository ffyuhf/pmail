## 1. 目标与变更范围

### 1.1 要改什么

将上游母项目（`母项目/PMail/`，模块路径 `github.com/Jinnrry/pmail`）相对现有项目（模块路径 `github.com/ffyuhf/pmail`）的三块代码改进，以**合并式移植**（保留现有项目自有增强）方式同步到现有项目：

**A. 规则转发功能重构**
- `services/rule/rule.go`：`DoRule` 签名增加 `rawEmailData []byte` 参数；FORWARD 分支重写为 `doForward`（地址解析验证、`isLocalDomain` 多域名判断、`forwardToLocalUser` 本地用户幂等投递、账户级自环检测、`ForwardRaw` 优先并降级 `Forward`）；新增 `doMove` 系统文件夹移动逻辑（INBOX/Sent/Drafts/Deleted/Junk 含 `Email.type` 同步更新，替代现有仅更新 `group_id` 的实现）。
- `utils/send/send.go`：新增 `ForwardRaw`（原始字节转发）与 `forwardData` 辅助函数；`Forward` 改为以本地用户身份（`user.Account@Domains[0]`）作为 envelope from 投递（修复现有以原发件人身份投递导致的 SPF 拒信/伪造问题）。
- `dto/parsemail/email.go`：`ForwardBuildBytes` 增加第 3 参数 `forwardAddress` 并重写头部（From=转发用户、Reply-To=原发件人、`X-Original-From`/`X-Forwarded-By`/`X-Forwarded-To`、`References`/`In-Reply-To` 关联原邮件）；**保留**现有项目的 `charset=UTF-8` 与 `Content-Transfer-Encoding: base64` 修复。
- `listen/smtp_server/read_content.go`：`rule.DoRule` 调用处传入 `emailData`。

**B. 邮件认证体系（EmailAuthentication）**
- `dto/parsemail/email.go`：新增 `EmailAuthentication` 结构体（SPFPassed/DKIMPassed/Dangerous）与 `NewEmailAuthentication` 工厂函数；`Email` 结构体新增 `Authentication` 字段；`NewEmailFromModel` 为收件邮件（Type==0）恢复认证结果，发件邮件保持 nil。
- `listen/smtp_server/read_content.go`：收信流程在解析后、每个钩子调用前后设置/重置 `email.Authentication`（防止插件篡改认证结果）；`saveEmail` 开头增加收信路径认证隔离（收信以 Authentication 为准，发件路径参数不被污染）。
- `hooks/framework`：`HookDTO` 结构不变（`Email` 内嵌 `Authentication` 后自动随序列化携带），移植 `framework_test.go` 验证序列化兼容。

**C. 列表接口小修复**
- `controllers/email/list.go`：移植 sender 空值回退（Sender 头为空时回退使用 `FromAddress`/`FromName`）；`Dangerous` 字段改用统一的 `NewEmailAuthentication` 入口（与现有 `SPFCheck==0 && DKIMCheck==0` 逻辑等价）。

**D. 测试移植**（import 路径 `github.com/Jinnrry/pmail` → `github.com/ffyuhf/pmail`）
- `dto/parsemail/email_authentication_test.go`、`dto/parsemail/email_forward_test.go`
- `listen/smtp_server/email_authentication_test.go`
- `services/rule/rule_forward_test.go`
- `hooks/framework/framework_test.go`
- 核查 `hooks/spam_block/spam_block_test.go` 适用性后决定是否移植

### 1.2 不改什么

- **现有项目自有增强全部保留，不做覆盖**：DSN 退信（RFC 3461）、From 伪装拒绝、Sender 头伪造检测、`pmailLog` 结构化日志、`ForwardBuildBytes` 的 base64 编码修复、列表接口 `UeId`/`Type` 字段。
- 不改动 `models/`（`SPFCheck`/`DKIMCheck` 字段、`models.INBOX` 等系统文件夹常量均已存在，无需变更）。
- 不改动数据库表结构（无 schema 变更）。
- 不改动前端（`fe/` 为 TS 重写版，`Dangerous` 标记已消费；本地转发对前端透明；母项目 `fe/` 为 JS 旧版不可直接套用）。
- 不改动 `hooks/framework` 的 `EmailHook` 接口签名。
- 不引入母项目与现有项目无关的其他文件差异。

## 2. 影响评估与依赖

### 2.1 影响的现有功能

| 影响点 | 说明 | 风险等级 |
|--------|------|----------|
| 规则 FORWARD 行为变化 | 旧逻辑仅做 `strings.Contains(rule.Params, Domain)` 防循环（会误杀子域地址转发）；新逻辑账户级自环检测 + 本地用户直接入库投递 + 远程原始转发。已配置转发规则的用户行为会改变（更正确） | 中 |
| 规则 MOVE 行为变化 | 旧逻辑仅更新 `group_id`；新逻辑对系统文件夹目标同步更新 `Email.type` 与 `UserEmail.status` | 中 |
| `DoRule` 签名变更 | 编译级影响，唯一调用方为 `read_content.go`，随本次一并修改 | 低 |
| `ForwardBuildBytes` 签名变更 | 唯一调用方为 `send.Forward`，随本次一并修改 | 低 |
| 转发邮件外观变化 | 转发邮件 From 变为转发者本人、Reply-To 指向原发件人、新增三个 X- 转发头 | 低（预期行为） |
| 收信认证链路 | 钩子（spam_block 等）在 `ReceiveParseAfter` 中对 `email.Status` 的修改仍有效，但认证结果字段不受插件影响；`ReceiveSaveAfter` 收到的 email 携带权威认证结果 | 低 |

### 2.2 依赖关系

- `rule.go` → `send.ForwardRaw`/`Forward` → `parsemail.ForwardBuildBytes`（签名级联，需按 todo 顺序实施）。
- `doMove` → `models.INBOX/Sent/Drafts/Deleted/Junk`、`consts.EmailTypeReceive/EmailTypeSend/EmailStatusDrafts/EmailStatusDel/EmailStatusJunk`（已确认在现有项目存在）。
- `forwardToLocalUser` → `models.UserEmail`、`models.User`（已存在，含 `disabled` 字段）。
- 测试依赖：`modernc.org/sqlite`、`xorm.io/xorm`（现有 go.mod 已包含，`rule_forward_test.go` 使用内存 SQLite）。

### 2.3 兼容性结论

- 无数据库 schema 变更；无 API 破坏性变更（`/email/list` 响应字段仅新增不变减）；插件二进制兼容（HookDTO 字段只增不改）。

## 4. 回滚方案与失败判定

### 4.1 回滚方案

- 现有项目已初始化 git 仓库（见 `docs/04-模块/docs/git仓库初始化_新增_20260815_17-37-00_v1.0.md`）：实施前确认工作区干净并记录当前 commit；任一步骤失败执行 `git checkout -- <文件>` 逐文件回滚，或整体 `git reset --hard` 回到基线 commit。
- 计划书与代码修改文档不回滚，标记【已作废】移入归档目录。

### 4.2 失败判定

出现任一情形即判定失败并停止后续步骤：
1. `go build ./...` 出现编译错误且无法在 2 次修正内解决。
2. 移植的任一测试用例失败且确认为移植代码缺陷（非环境问题）。
3. 现有测试套件（`email_test.go`、`email_xss_test.go`、`dkim_test.go` 等）出现回归失败。
4. diff 审查发现现有项目自有增强（DSN/防伪造/结构化日志/base64 修复）被意外删除。
