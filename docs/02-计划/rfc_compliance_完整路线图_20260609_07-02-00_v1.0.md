## 1. 目标与变更范围

### 1.1 总体目标

将 PMail 项目的 IMAP/SMTP 服务逐步提升至主流 RFC 标准合规水平，确保与现代邮件客户端的广泛兼容性。

### 1.2 已完成工作（P0/P1）

以下工作已在前期完成，不在本路线图范围内：

| 编号 | 内容 | RFC | 完成日期 | 状态 |
|------|------|-----|----------|------|
| P0-1 | SMTP 启用 SMTPUTF8 | RFC 6531 | 2026-06-09 | ✅ 已完成 |
| P0-2 | IMAP 启用 LITERAL+ | RFC 7888 | 2026-06-09 | ✅ 已完成 |
| P1-1 | IMAP 启用 ESEARCH | RFC 4731 | 2026-06-09 | ✅ 已完成 |

**参考文档**：
- `docs/02-计划/rfc_compliance_P0_P1_修复计划_20260609_06-30-00_v1.0.md`
- `docs/04-模块/smtp_server/smtp_EnableSMTPUTF8_新增_20260609_06-30-00_v1.0.md`
- `docs/04-模块/imap_server/imap_server_RFC扩展_修正_20260609_06-30-00_v1.0.md`

### 1.3 本路线图覆盖范围

| 阶段 | 优先级 | RFC | 目标 | 预估工期 | 复杂度 |
|------|--------|-----|------|----------|--------|
| 阶段二 | P1 | RFC 6409 | 邮件提交协议 DSN 补全 | 3-5天 | 中 |
| 阶段三 | P2 | RFC 7162 | CONDSTORE 增量同步 | 2-3周 | 高 |
| 阶段四 | P3 | RFC 9051 | IMAP4rev2 升级 | 待评估 | 极高 |

### 1.4 不改什么

- **不修改** go-imap/v2 或 go-smtp 库源码（使用库提供的扩展接口）
- **不修改**前端代码（本路线图仅涉及后端协议层）
- **不修改** HTTP API 层（RFC 合规性改进不影响 REST 接口）
- **不涉及** POP3 协议（POP3 由独立的 `gopop` 库处理）

## 3. 阶段二：RFC 6409 DSN 补全（P1）

### 3.1 目标

为 SMTP 邮件提交服务添加 DSN（Delivery Status Notification，投递状态通知）支持，使 RFC 6409 合规度从 85% 提升至 95%+。

### 3.2 涉及文件

```
server/
├── listen/
│   └── smtp_server/
│       ├── smtp.go           # 三个 SMTP 实例添加 EnableDSN = true
│       └── action.go         # Rcpt 方法处理 NOTIFY/ORCPT 参数
├── utils/
│   └── send/
│       └── send.go           # 发送失败时生成 DSN 退信报告
└── services/
    └── dsn/                  # 新建：DSN 报告生成服务
        └── dsn.go            # RFC 3462 格式的 multipart/report 生成
```

### 3.3 实施步骤

#### 步骤 1：SMTP 启用 DSN 声明

**修改文件**：`server/listen/smtp_server/smtp.go`

**变更内容**：在三个 SMTP 实例创建后添加 `EnableDSN = true`

```go
// 端口 587（STARTTLS 提交）
instanceTlsNew.EnableDSN = true

// 端口 465（隐式 TLS 提交）
instanceTls.EnableDSN = true

// 端口 25（外部接收）— 仅提交服务需要，但保持一致
instance.EnableDSN = true
```

**影响**：EHLO 响应中将公布 `DSN` 能力；RCPT TO 命令可接受 `NOTIFY` 和 `ORCPT` 参数。

#### 步骤 2：处理 RCPT TO 的 DSN 参数

**修改文件**：`server/listen/smtp_server/action.go`

**变更内容**：在 `Rcpt` 方法中记录 DSN 参数

```go
// 需要在 Session 结构体中新增字段：
type Session struct {
    // ... 现有字段
    DSNNotifications map[string]*smtp.RcptOptions  // 收件人 → DSN 选项
}

// Rcpt 方法中记录 DSN 请求
func (s *Session) Rcpt(to string, opts *smtp.RcptOptions) error {
    if opts != nil && (len(opts.Notify) > 0 || opts.OriginalRecipient != "") {
        if s.DSNNotifications == nil {
            s.DSNNotifications = make(map[string]*smtp.RcptOptions)
        }
        s.DSNNotifications[to] = opts
    }
    // ... 现有逻辑
}
```

#### 步骤 3：实现 DSN 报告生成

**新建文件**：`server/services/dsn/dsn.go`

**功能**：根据 RFC 3462 生成 `multipart/report` 格式的退信通知

```go
// GenerateDSN 生成投递状态通知邮件
// 参数：原始邮件信息、失败原因、收件人、发件人域名
// 返回：RFC 3462 格式的 DSN 报告（MIME multipart/report）
func GenerateDSN(originalFrom, originalTo, originalMsgID string,
    failureReason error, domain string) ([]byte, error)
```

#### 步骤 4：发送失败时触发 DSN

**修改文件**：`server/listen/smtp_server/read_content.go`

在发送失败的处理逻辑中（第116-138行），当收件人请求了 DSN 通知时，生成并发送退信报告。

### 3.4 风险评估

| 风险项 | 等级 | 缓解措施 |
|--------|------|----------|
| DSN 报告格式不正确 | 低 | 严格遵循 RFC 3462，编写单元测试 |
| 退信循环（DSN 本身发送失败） | 中 | 对 DSN 邮件标记 `Auto-Submitted: auto-replied`，不对其生成 DSN |
| 性能影响 | 低 | DSN 生成仅在失败时触发，影响可忽略 |

### 3.5 验收标准

- [x] EHLO 响应包含 `DSN` 能力
- [x] RCPT TO 接受 `NOTIFY=SUCCESS,FAILURE` 和 `ORCPT=...` 参数
- [x] 发送失败时生成 RFC 3462 格式的退信通知
- [x] 退信通知正确路由到原始发件人
- [x] 编译通过、现有测试通过

## 4. 阶段三：RFC 7162 CONDSTORE 实现（P2）

### 4.1 目标

实现 IMAP CONDSTORE 扩展，支持基于 mod-sequence 的增量邮箱同步，显著改善移动客户端和大邮箱用户的断线重连体验。

### 4.2 技术方案

#### 4.2.1 数据模型变更

**修改文件**：`server/models/user_email.go`

```go
// 新增字段
type UserEmail struct {
    // ... 现有字段
    ModSeq int64 `xorm:"modseq bigint notnull default(0) index comment('IMAP CONDSTORE 修改序列号')"`
}
```

**新增计数器表**：

```go
// server/models/modseq_counter.go（新建）
type ModSeqCounter struct {
    ID      int   `xorm:"id pk autoincr"`
    UserID  int   `xorm:"user_id int notnull unique index"`
    Mailbox string `xorm:"mailbox varchar(255) notnull unique index"`  // 邮箱名
    ModSeq  int64 `xorm:"modseq bigint notnull default(0)"`
}
```

### 4.4 分阶段实施策略

由于 CONDSTORE 复杂度高，建议分两期实施：

#### 期一：基础 CONDSTORE（1.5-2周）

- 数据库变更 + modseq 分配器
- SELECT 返回 HIGHESTMODSEQ
- FETCH 支持 CHANGEDSINCE
- STORE 更新 modseq
- 新邮件到达时设置初始 modseq

#### 期二：QRESYNC + 完善（1周）

- CapSet 添加 `CapQResync`
- 实现 QRESYNC 快速重新同步
- SEARCH 支持 MODSEQ 条件
- 端到端测试（使用真实客户端验证）

### 4.5 风险评估

| 风险项 | 等级 | 缓解措施 |
|--------|------|----------|
| 数据库迁移影响现有部署 | 高 | modseq 默认值为 0，不影响现有数据；新增字段为非破坏性变更 |
| modseq 计数器并发竞争 | 中 | 使用数据库行锁或 Redis 原子操作 |
| FETCH 性能下降 | 中 | modseq 字段建立索引；CHANGEDSINCE 过滤在数据库层完成 |
| go-imap/v2 beta 版本 API 变动 | 低 | 锁定依赖版本，关注库更新 |

## 5. 阶段四：RFC 9051 IMAP4rev2 升级（P3）

### 5.1 目标

将 IMAP 协议从 IMAP4rev1（RFC 3501）升级到 IMAP4rev2（RFC 9051），支持新一代邮件客户端。

### 5.2 IMAP4rev2 隐含能力清单

IMAP4rev2 将以下扩展整合为协议核心，**必须全部支持**：

| 隐含能力 | 当前状态 | 需要的工作 |
|----------|---------|-----------|
| `NAMESPACE` | ✅ 已实现 | 无需变更 |
| `UNSELECT` | ✅ 已实现 | 无需变更 |
| `UIDPLUS` | ✅ 已实现 | 无需变更 |
| `ESEARCH` | ✅ 已实现 | 无需变更 |
| `SEARCHRES` | ❌ 未实现 | 需新增：搜索结果引用 |
| `ENABLE` | ✅ 库自动 | 无需变更 |
| `IDLE` | ✅ 已实现 | 无需变更 |
| `SASL-IR` | ✅ 库自动 | 无需变更 |
| `LIST-EXTENDED` | ❌ 未实现 | 需新增：扩展 LIST 选项 |
| `LIST-STATUS` | ❌ 未实现 | 需新增：LIST 同时返回 STATUS |
| `MOVE` | ✅ 已实现 | 无需变更 |
| `LITERAL-` | ✅ 库自动 | 无需变更 |
| `STATUS=SIZE` | ❌ 未实现 | 需新增：STATUS 返回 SIZE |
| `CONDSTORE` | ❌ 未实现 | 阶段三完成后可用 |

### 5.3 涉及文件

```
server/
├── listen/
│   └── imap_server/
│       ├── imap_server.go      # CapSet 替换为 CapIMAP4rev2
│       ├── session_search.go   # 支持 SEARCHRES（搜索结果引用）
│       ├── session_list.go     # 支持 LIST-EXTENDED 选项
│       └── session_status.go   # 支持 STATUS=SIZE
└── services/
    └── group/
        └── group.go            # GetGroupStatus 添加 SIZE case
```

### 5.4 前置条件

- **阶段三完成**：IMAP4rev2 隐含 CONDSTORE，必须先完成阶段三
- **go-imap/v2 正式发布**：当前为 beta.5，API 可能变动，建议等待正式版
- **SEARCHRES 实现**：需 go-imap/v2 库支持搜索结果引用

### 5.5 风险评估

| 风险项 | 等级 | 缓解措施 |
|--------|------|----------|
| go-imap/v2 库 API 大幅变动 | 高 | 等待正式版发布后再评估 |
| 部分旧客户端不支持 IMAP4rev2 | 中 | 同时声明 IMAP4rev1 和 IMAP4rev2（库支持双声明） |
| SEARCHRES 实现复杂 | 中 | SEARCHRES 允许将搜索结果保存并在后续命令中引用，需维护会话级搜索状态 |

### 5.6 实施建议

- **建议时机**：go-imap/v2 发布正式版后（预计 2026 Q3-Q4）
- **预估工期**：3-4周（含 SEARCHRES、LIST-EXTENDED、LIST-STATUS、STATUS=SIZE 的实现）
- **建议策略**：先实现各独立扩展能力（SEARCHRES、LIST-EXTENDED 等），测试通过后再切换 CapSet 为 IMAP4rev2
