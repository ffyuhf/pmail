## 1. 目标与变更范围

### 1.1 目标

对母项目（`母项目/PMail/`，模块 `github.com/Jinnrry/pmail`）相对现有项目（`PMail/`，模块 `github.com/ffyuhf/pmail`）的全部代码改进进行**系统性全面核查**，将所有未移植的改进以**合并式移植**（保留现有项目自有增强）方式同步到现有项目，并产出可审计的《母项目改进移植完整性核查报告》，以文件级证据回答"所有改进是否已全部移植"。

背景：上一轮移植（v2.6，2026-08-15）覆盖 MIG-01~MIG-09（规则转发重构、EmailAuthentication、列表 sender 回退、spam_block 权限保护、6 份测试）。本轮规划阶段抽样已确认存在**上轮范围外的未移植改进**（见 1.2 T1），故必须全量 diff 核查，不能仅凭上轮清单收尾。

### 1.2 要改什么

**T1（已确认的未移植改进）：`services/list/list.go` `genSQL` 系统文件夹双条件查询**

与上轮移植的 `rule.doMove`（移动到系统文件夹时同步写 `group_id`）强配套的查询侧逻辑，现有项目缺失：

| 位置 | 母项目逻辑 | 现有项目现状 |
|------|-----------|-------------|
| Status 过滤 | `EmailStatusDel/Drafts/Junk` 三状态使用 `(ue.status =? or ue.group_id=?)` 双条件（匹配 models.Deleted/Drafts/Junk） | 仅 `and ue.status =?` 单条件，doMove 写入的 group_id 无法被查询命中 |
| Type 过滤 | `EmailTypeSend` 使用 `(type =? or ue.group_id=?)`（含 models.Sent） | 仅 `and type =?` |
| GroupId 过滤 | `GroupId==-1` 时 `(ue.group_id=0 or ue.group_id=INBOX)`；`GroupId==0 && Status==-1` 时 `(ue.group_id=? or ue.group_id=0)` | 仅 `group_id=?` / `group_id=0` 单条件 |

移植时**必须保留**现有项目自有修复：LIKE 通配符转义（20260610 #15）、`ue.id as ue_id` 查询列、`GroupId>0` 自定义分组免 status 过滤（20260516 修复）——两套逻辑需语义级合并。

**T2（待全量 diff 后确定的 A 类改进项）**

对 server 下全部同构 Go 文件及根级构建文件逐一 diff，凡判定为"母项目改进且现有项目缺失"（A 类）的，逐项合并移植。候选重点区域（抽样未覆盖/未结论）：`listen/imap_server/*`（如 `session_fetch.go` 的 Envelope/BodyStructure 实现）、`listen/pop3_server/*`、`listen/smtp_server/{action,login}.go`、`controllers/*`（除 email/list.go）、`services/{detail,group,del_email,attachments,auth,setup}/*`、`hooks/*`（除 spam_block 权限）、`dto/response/*`、`utils/*`、`models/*`、`db/init.go`、`i18n/i18n.go`、`res_init/init.go`、`session/init.go`、`signal/signal.go`、`consts/consts.go`、`main.go`、`main_test.go`、构建文件（Makefile/Dockerfile/DockerfileGithubAction/.github/）。

**T3（配套文档与核查报告）**

按第 5 章清单创建代码修改文档、变更日志 v2.7、《母项目改进移植完整性核查报告》。

### 1.3 不改什么

- **前端 `fe/` 完全排除**：母项目 `fe/` 为 JavaScript 旧版（vite.config.js/main.js），现有项目为 TypeScript 重写版（vite.config.ts/main.ts + services/stores 分层），架构不同不可直接套用（延续上轮共识）。
- **现有项目自有增强全部保留、不做覆盖**：DSN 退信（RFC 3461）、From 伪装拒绝、Sender 头伪造检测、`pmailLog` 结构化日志、SMTPUTF8、60s 收发超时、LIKE 转义、`UeId`/`Type` 响应字段、`ForwardBuildBytes` base64/charset 修复、`services/dsn` 包、`utils/log` 包。
- `go.mod`/`go.sum`：双侧依赖清单完全一致，仅 module 名不同，不改。
- 数据库表结构（无 schema 变更预期；若 diff 发现母项目 `models` 字段变更，单独升级为审批项）。
- 母项目非代码文件：`README*`、`docs/`（gif/jpg）、`fe/.vscode`、`LICENSE`。
- 母项目**独有但现有项目已重构替代**的目录结构差异不搬运（如母项目 `utils/consts` vs 现有项目 `consts`——以现有为准，仅比对重叠实体内容）。

## 2. 影响评估与依赖

### 2.1 风险与应对

| 风险 | 说明 | 应对 |
|------|------|------|
| R1 母项目代码库不完整 | 母项目 import `github.com/Jinnrry/pmail/config` 但其 `server/` 下无 `config` 包，母项目无法独立编译 | 禁止整目录覆盖；仅做单文件级合并移植；移植后以现有项目 `go build ./...` 为唯一编译基准 |
| R2 genSQL 语义合并冲突 | 现有 20260516 修复（GroupId>0 免 status 过滤）与母项目 Status/Type/GroupId 三处双条件交织 | 按"母项目条件结构为骨架 + 现有三项自有修复嵌入"顺序合并；合并后用对照用例验证（收件箱/发件箱/已删除/草稿/垃圾/自定义分组×删除状态） |
| R3 误判差异性质 | 约 130 个同构文件中，现有项目领先（如 `smtp.go`）、母项目领先（如 `list.go` genSQL）、仅注释差异三类混杂 | 强制三分类判定表（A 移植 / B 保留 / C 忽略），每项记录判定依据；B/C 类不触碰代码 |
| R4 回归风险 | 移植触碰 IMAP/POP3 查询路径 | 移植前后各跑一次全量 `go test ./...`，基线差异逐包比对 |

### 2.2 依赖关系

- T1 依赖上轮已就位的 `models.INBOX/Sent/Drafts/Deleted/Junk` 常量与 `consts.EmailStatusDel/Drafts/Junk`、`consts.EmailTypeReceive/Send`（已确认双侧存在）。
- `list.go` genSQL 变更影响消费方：`controllers/email/list.go`（网页列表）、`pop3_server`（Stat/getList pop3List 路径）、IMAP 侧 `GetEmailListByGroup`（不走 genSQL，无影响）——需在验证阶段覆盖网页列表与 POP3 列表两条路径。
- 全量 diff 依赖现有项目 git 基线（`main` 分支，首次提交 `1ccc9ac` + v2.6 提交）用于回滚。

## 4. 回滚方案与失败判定

### 4.1 回滚方案

- 实施前确认 `git status` 干净并记录当前 commit；每个移植项独立 commit。
- 单项回滚：`git checkout -- <文件>`；整体回滚：`git reset --hard <基线commit>`。
- 计划书与修改文档不回滚，如计划废止则标记【已作废】移入 `02-计划/归档/`。

### 4.2 失败判定（任一命中即停止并回退）

1. `go build ./...` 编译错误且 2 次修正内无法解决。
2. 移植新增/既有测试出现失败且确认为移植代码缺陷（非 v2.6 已记录的环境性失败）。
3. diff 审查发现现有项目自有增强（1.3 节清单）被意外删除或削弱。
4. genSQL 合并后网页列表/POP3 列表对照用例出现语义回归（文件夹视图漏邮件/多邮件）。
